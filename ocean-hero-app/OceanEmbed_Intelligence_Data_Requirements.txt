OceanEmbed — Intelligence Page
Data & AI Integration Requirements
Exact inputs required for Fisheries, Ocean Health, Offshore and Maritime Intelligence
1. Purpose
This document is the integration specification for OceanEmbed's Intelligence page. It tells the frontend/backend/ML team exactly where live surface data, OceanEmbed AI subsurface predictions, reference data and derived calculations are required. The objective is to connect the real trained model later without changing the four Intelligence features.
2. Core concept
OceanEmbed follows Observe → Reconstruct → Understand → Decide. The Intelligence page is the application layer: it takes physical ocean observations plus reconstructed subsurface temperature and converts them into domain-specific decision support.
Pipeline:
Data sources → harmonization → surface ocean state → OceanEmbed AI → subsurface temperature profile → derived physical features → module-specific analysis → Intelligence UI.
3. MOST IMPORTANT: where the AI model output is needed
CRITICAL: HYCOM/GLORYS subsurface temperature must NOT be labelled 'OceanEmbed prediction' unless the trained OceanEmbed model actually produced it. Reanalysis can be used as reference/validation data.
If the trained model is unavailable, invalid at a location, or does not provide a requested depth, return INSUFFICIENT DATA / DATA NOT AVAILABLE. Never create fake values.
4. Common ocean readings
5. Fisheries Intelligence
Question answered: 'Are the physical ocean conditions environmentally favorable for fishing-related activity at this location?' It does NOT detect fish, identify species, estimate abundance or guarantee a fishing location.
Overall suitability is a weighted environmental indicator. Prototype classes: FAVORABLE, MODERATE, LESS SUITABLE, INSUFFICIENT DATA. The ranges and weights require fisheries-specific validation before being described as validated fishing guidance.
6. Ocean Health Intelligence
Question answered: 'Are the physical ocean conditions unusual compared with an appropriate reference?' This is physical-condition monitoring, not a complete biological ecosystem-health diagnosis.
Depth selectors: 0–200 m, 200–600 m, 600–900 m, 900–1000 m.
Status classes: NORMAL, ELEVATED, UNUSUAL, INSUFFICIENT DATA. Exact thresholds must be defined from a suitable climatology/baseline. A cross-depth comparison must NOT be called a true anomaly.
Possible physical processes can be shown as investigation hypotheses: water-mass movement/subduction, mesoscale eddy activity, vertical mixing, upwelling variability, and marine heat events. Do not automatically attribute anomalies to pollution, volcanoes or climate change.
7. Offshore Intelligence
Question answered: 'What are the ocean conditions at this offshore site and how do they vary through the water column?' This supports planning/monitoring; it is NOT engineering safety certification.
Presets currently discussed: Arabian Sea Sector, Krishna–Godavari Deep Water, Lakshadweep Ridge Channel.
8. Maritime Intelligence
Question answered: 'How do ocean currents and water geography affect a route between two selected locations?' Current version = prototype water-constrained/current-aware route analysis, NOT globally optimal routing and NOT autonomous navigation.
Current effect classes: FAVORABLE, OPPOSING, MIXED, DATA NOT AVAILABLE. Current UI should show ✓ CURRENT and unavailable factors such as — WIND, — WAVES, — WEATHER until real datasets are integrated.

10. Derived calculations the backend should expose
Current speed = sqrt(U² + V²).
Current direction = vector direction derived from U and V.
Vertical temperature gradient = temperature change / depth interval.
Thermocline indicator = derived from the vertical temperature gradient; exact algorithm must be fixed before claiming a scientific thermocline detector.
True temperature anomaly = OceanEmbed T at depth − reference T at the same depth.
Route-current effect = current vector component relative to route direction; define the sign convention before classifying favorable/opposing.
Route distance = length of the analyzed water route.

12. Minimum data checklist before each feature is 'fully live'
Fisheries: SST + SSS + current U/V + valid OceanEmbed subsurface profile + defined/validated suitability logic.
Ocean Health: valid OceanEmbed profile + same-depth reference baseline + anomaly thresholds + supporting SSS/current/SSH where available.
Offshore: SST + SSS + current U/V + OceanEmbed temperatures at 200/500/1000 m or full profile + compatible GLORYS reference + anomaly logic.
Maritime: valid A/B water points + land/water mask + water-constrained route engine + current U/V along route.

14. Scientific/UI rules
Never fabricate missing ocean readings.
Show source/provenance where practical.
Do not label HYCOM/GLORYS as OceanEmbed prediction unless the trained model produced the value.
Use same-depth baselines for true subsurface temperature anomalies.
Do not call a simple current difference 'divergence' unless spatial divergence is actually calculated.
Prototype fisheries thresholds/weights must be labelled as prototype until validated.
Fisheries = environmental suitability, not fish detection.
Ocean Health = unusual physical conditions, not complete ecological health.
Offshore = planning/monitoring support, not engineering certification.
Maritime = decision support, not autonomous navigation.

16. One-line integration rule for the AI developer
Whenever a feature asks for subsurface temperature, depth-specific temperature, thermocline/profile structure or subsurface anomaly, feed it the actual OceanEmbed model prediction; use live surface providers for SST/SSS/current/SSH; use GLORYS/HYCOM as explicitly labelled reference data; and return INSUFFICIENT DATA whenever a required real value is unavailable.
